# Модуль 7 — Observability та Evaluation

Продовження модуля 6. **Додається:** eval-датасет + гейт замість ручної
перевірки — і найсильніший момент курсу: тиха деградація.

## Нове відносно модуля 6

- `modules/m07_evaluation.py` — 14 кейсів по 5 долях посилок; на кожен дві
  незалежні перевірки: чи викликано правильний інструмент (детерміновано,
  безкоштовно) і LLM-judge за критерієм (дешева модель, temperature=0,
  суддя бачить УСЮ базу правил). Гейт: 0.8.
- `data/evalset.json` — сам датасет.
- `degradation_demo.py` — агент не змінювався, «вийшов реліз API v2»
  бекенду (дні від останнього сканування, статуси перекодовано). Логи
  чисті, відповіді впевнені — гейт падає: 14/14 → 10/14 на живому прогоні.
- `eval_history.py` — «до/після» у `out/eval_history.jsonl`: скор сам по
  собі не значить нічого, значить дельта.
- `langfuse_tracer.py` — той самий Tracer, спани їдуть у Langfuse
  (без ключів деградує до локального).
- `otel_tracing.py` — **одна інструментація, чотири бекенди**: спани за
  домовленостями OTel GenAI (`invoke_agent` → `execute_tool` → `chat`),
  а куди вони летять — питання експортера, не коду агента.
- `test_eval_gate.py` — евали як звичайний pytest: червоний тест = реліз
  не проходить. Те саме, що робить DeepEval у CI, на нашому судді.

## Запуск

```bash
python run.py 7                             # eval + гейт
python otel_tracing.py                      # трейси в консоль, нічого не треба
python otel_tracing.py --backend phoenix    # локальний UI, див. нижче про оточення
python otel_tracing.py --backend langfuse   # те саме в хмару, лише за ключами
pytest test_eval_gate.py -q                 # гейт як CI-тест (~2,5 хв)
python online_eval.py                       # оцінки на живі трейси (треба Langfuse)
python eval_history.py baseline     # записати прогін
python degradation_demo.py          # зірка курсу (~2×28 LLM-викликів)
python eval_history.py --compare
```

## Одна інструментація — різні бекенди

`otel_tracing.py` показує тезу модуля буквально: агент інструментований
один раз за семантичними домовленостями OpenTelemetry, а бекенд
міняється прапорцем, а не переписуванням коду.

| Прапорець | Куди летять спани | Що треба |
|---|---|---|
| `--backend console` | у термінал | нічого |
| `--backend phoenix` | локальний Arize Phoenix, UI на :6006 | окреме оточення, див. нижче |
| `--backend langfuse` | Langfuse Cloud або свій self-host | `LANGFUSE_PUBLIC_KEY` + `LANGFUSE_SECRET_KEY` |
| `--backend langsmith` | LangSmith | `LANGSMITH_API_KEY` (+ `LANGSMITH_HOST` для ЄС) |
| `--backend otlp` | Datadog, Grafana, Jaeger, свій колектор | `OTEL_EXPORTER_OTLP_ENDPOINT` (+ `_HEADERS`) |

Відкрийте `_exporter()` і подивіться на гілки поруч: **різниця між
бекендами — це ендпоінт і заголовок авторизації, більше нічого.** Langfuse
авторизує звичайним Basic, LangSmith — заголовком `x-api-key`, Phoenix
локально не авторизує взагалі. Жоден із них не вимагає свого SDK і не
знає про наш код.

Якщо ключів немає — кожен бекенд скаже, чого саме бракує і де це взяти,
а не впаде трейсбеком.

Ключі, які є, перевіряються ДО експорту. Це не зайва обережність:
`BatchSpanProcessor` не показує помилок доставки, тож без перевірки
відмова доступу виглядала б як порожній дашборд, і причину ви шукали б
у коді агента. Найчастіша пастка — регіон LangSmith: ключ із ЄС на
американському хості дає 403, і трейси просто зникають.

### Phoenix ставиться в ОКРЕМЕ оточення

Не в те, де живе агент:

```
python3 -m venv ~/.venv-phoenix
~/.venv-phoenix/bin/pip install arize-phoenix
~/.venv-phoenix/bin/phoenix serve          # UI на :6006
```

Причина технічна й повчальна водночас. Технічна: Phoenix тягне
`fastmcp-slim`, який вимагає `mcp<2.0`, а нам для модуля 5 потрібен
`mcp[cli]>=2.1` — в одному оточенні вони не стають. Повчальна: Phoenix
і не мусить там жити. Це окремий процес-приймач, який слухає OTLP по
HTTP. Ваш агент не імпортує Phoenix і нічого про нього не знає — він
просто шле спани на `localhost:6006`. Рівно так само, як шле їх у
Langfuse чи Datadog.

Чого це коштує, щоб ви вирішували свідомо: ~795 МБ і 152 пакети в
окремому оточенні, стартує за кілька секунд. Натомість це єдиний бекенд
у практиці, якому не потрібні ні акаунт, ні ключі, ні інтернет — дані
лишаються у вас на машині, у `~/.phoenix/phoenix.db`.

Якщо ставити не хочеться — не ставте. Консольного бекенда достатньо,
щоб побачити все, що треба; хмарні дадуть той самий трейс, якщо у вас
є ключі.

Спани й атрибути — рівно ті, що в домовленостях OTel GenAI, і рівнів
там три:

```
invoke_agent agentpro-support-agent      ← увесь виклик агента
├── chat claude-sonnet-4-6               ← звернення до моделі, тут токени
├── execute_tool get_order_status        ← інструмент
├── execute_tool check_refund_eligibility
├── chat claude-sonnet-4-6
└── chat claude-haiku-4-5                ← guardrail теж модель, теж гроші
```

Третій рівень важливий: без спанів `chat` бекенд не знає ні про токени,
ні про вартість, і дашборд показує нулі. З ними Langfuse сам розкладає
прогін на GENERATION / TOOL / AGENT і рахує ціну — жодного його SDK у
коді немає, він читає самі лише домовленості.

Зверніть увагу на останній рядок: guardrail із модуля 6 — це ще одне
звернення до моделі. Захист має ціну, і тепер вона видима.

> Влітку 2026 конвенції переїхали з головного репозиторію OTel в окремий —
> [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai),
> файл `docs/gen-ai/gen-ai-agent-spans.md`. Старі посилання на
> `opentelemetry.io/docs/specs/semconv/gen-ai/` ведуть на заглушку «Moved».

## Евали як тести

`pytest test_eval_gate.py` — 14 кейсів, на кожен дві перевірки:

- **вибір інструмента** — перевірка детермінована й безкоштовна, але сам
  вибір робить модель, тож поодинокий промах трапляється;
- **зміст відповіді** — перевіряє суддя, а він теж модель і на межі
  хитається: на прогонах поспіль гейт стабільно давав 13/14, але падав
  щоразу інший кейс.

Тому покейсово обидві перевірки — `xfail`, тобто сигнал подивитись, а не
зупинка збірки. Блокують **два агрегати**: `tool accuracy ≥ 0.9` і
`гейт ≥ 0.8`. Так червоне означає справжнє погіршення, а не шум моделі —
інакше на занятті збірка червоніла б через раз.

Прапорець `--deepeval-gate` додатково проганяє три кейси через DeepEval —
щоб побачити різницю в API. Потребує окремого ключа для його судді.

## Історія, яку варто розповісти групі

Важіль деградації шукали чотири рази: вимкнений retrieval, викинуті
тексти правил і «інструменти дорогі, викликай рідше» деградації НЕ дали —
політика продубльована в типізованих полях бекенду, а суддя без
temperature=0 хитав гейт (одного разу «деградований» прогін обігнав
здоровий). Спрацював лише дрейф даних — найчесніший продакшн-сценарій.
Мораль: eval ловить деградацію ДАНИХ, не лише промптів → online-евали.

**Далі (модуль 8):** агент якісний, виміряний і захищений — але живе
на ноутбуці ментора.

## Евал поверх трейсів — те, що зшиває дві половини модуля

`test_eval_gate.py` міряє те, що ви **передбачили** в датасеті. У проді
приходять запити, яких там немає, і саме на них агент ламається
найцікавіше. `online_eval.py` замикає цикл:

```bash
python online_eval.py              # живі запити → трейси → оцінки на них
python online_eval.py --degraded   # те саме, але на дрейфі даних з demo 4
python online_eval.py --collect    # погані трейси → data/from_traces.json
```

Оцінка чіпляється **до того самого трейсу**, а не живе окремим числом.
У Langfuse 4 це просто: трейс — це той самий OTel-трейс, тож ідентифікатор
береться з поточного спана, нічого зшивати руками не треба:

```python
trace_id = format(root.get_span_context().trace_id, "032x")
lf.create_score(name="judge", value=0.0, trace_id=trace_id, comment=reason)
```

Далі в UI фільтруєте за `judge = 0` — і бачите не «щось зламалось», а
конкретні погані розмови, кожну з повним трейсом: які інструменти агент
брав, що вони повернули, скільки це коштувало.

`--collect` забирає ці трейси назад у датасет разом із причиною провалу
й посиланням на джерело. Це і є відповідь на питання «звідки брати
кейси»: не з голови, а з власних збоїв. Повторний збір не дублює вже
зібране.

`data/from_traces.jsonl` — кандидати, а не готовий датасет: критерій
там загальний. Перегляньте очима, звузьте його — і тоді перенесення
це один рядок:

```bash
cat data/from_traces.jsonl >> data/evalset.jsonl
```

## Чому датасет у JSONL

`data/evalset.jsonl` — основний файл, один кейс на рядок.

Для чотирнадцяти кейсів різниці з JSON-масивом немає. Вона починається
далі: дописати кейс — це дописати рядок, а не переписати весь файл;
у диффі видно саме доданий кейс, а не зсув усього масиву; двоє людей
дописують одночасно без конфлікту злиття. І це формат, який очікують
на вході LangSmith, promptfoo та решта — імпорт без конвертації.

`evalset.json` лишається поруч для сумісності. Читається `.jsonl`, якщо
він є. Щоб файли не розійшлись мовчки, у гейті є `test_dataset_files_agree`:
якщо ви відредагували один, а не обидва, тест назве, які саме кейси
розбіглись. Це дешевше, ніж два тижні дивуватись, чому правка не діє.
