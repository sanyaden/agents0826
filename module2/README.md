# Модуль 2 — RAG / Agentic RAG

Продовження модуля 1. **Додається шар знань:** агент починає цитувати
«Правило 4.2» замість вигадувати. Далі ми цей шар ламаємо і лагодимо
чотири рази поспіль — саме в цьому й полягає модуль.

Наскрізний запит той самий:

> «Посилка EE123456789UA не прийшла вже два тижні. Я хочу повернути гроші за доставку.»

---

## Встановлення

```bash
python3 -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env      # і впишіть ANTHROPIC_API_KEY
```

Базовий набір ставиться швидко: `anthropic`, `python-dotenv`,
`sentence-transformers`, `qdrant-client`. Важкий eval-стек (ragas +
langchain) — окремо і лише для останнього демо:

```bash
pip install -r requirements-eval.txt
```

> **Якщо `.venv` уже існує** — не запускайте `python -m venv` поверх нього,
> `ensurepip` впаде і оточення зламається. Спершу `rm -rf .venv`.
>
> **Перший запуск** качає модель ембедингів (~120 МБ). Зробіть це заздалегідь,
> далі вона береться з кешу.

## Демо по одному

### 1. Чанкінг: розмір і перетин

```bash
python chunking.py --compare
```

```
   25 ток. · перетин  0 →  8 чанків   A РВЕТЬСЯ  B РВЕТЬСЯ  C РВЕТЬСЯ
   40 ток. · перетин  0 →  5 чанків   A разом    B РВЕТЬСЯ  C разом
   60 ток. · перетин  0 →  4 чанків   A РВЕТЬСЯ  B РВЕТЬСЯ  C разом
   60 ток. · перетин 18 →  4 чанків   A разом    B разом    C разом
```

Три пари фактів, які мають лишатись разом (A: умова + сума, B: умова +
строк виплати, C: втрата + строк розшуку). **Ключовий рядок — 60 токенів:**
без перетину сума «120 грн» опиняється в одному чанку, а умова «5 і більше
днів» — у сусідньому, тож агент бачить половину правила. З перетином 18
токенів кількість чанків та сама, а факти знову разом. Це і є відповідь
на питання «навіщо overlap».

25 токенів не рятує навіть перетин — чанк менший за саме правило.
120 тримає все і без перетину, але тягне в промпт цілий розділ.

`python chunking.py` без прапорця показує самі чанки з підсвіткою перетину.

### 2. Де ламається лексика

```bash
python knowledge_vec.py
```

```
Запит: «Кур'єр загубив мій пакунок, що мені виплатять?»
  лексичний: Правило 4.5. Повернення здійснюється на той самий спосіб оплати…
  векторний (0.79): Правило 7.3. Компенсація за втрачене вкладення…
```

У базі написано «втрачено», клієнт каже «загубив» — префіксне порівняння
безсиле. Ембединги влучають. Інтерфейс (`retrieve` / `as_context`) той
самий, тож агент про заміну не знає.

Пороги можна подивитися окремо:

```bash
python -c "
import knowledge_vec as v
for s, t in v.scores('Кур\'єр загубив мій пакунок, що мені виплатять?', 4):
    print(f'{s:.4f}  {t[:70]}')"
```

```
0.7906  Правило 7.3. Компенсація за втрачене вкладення…   ← правильне
0.7778  Правило 4.5. Повернення на той самий спосіб оплати…
```

Різниця між правильним і хибним — **13 тисячних**, а поріг 0.78 проходить
рівно між ними. Звідси й правило: поріг тюниться на даних, не береться
з підручника.

### 3. Векторна БД (Qdrant)

```bash
python knowledge_qdrant.py            # вбудований режим :memory:
python knowledge_qdrant.py --filter   # лише правила про компенсацію
```

```
Сховище: :memory: (вбудований, без Docker)
Запит: «Яка погода у Львові?»
  — нічого понад поріг (fail-closed): агент не вигадуватиме правило
```

**Docker не потрібен, і жодного ключа теж** — Qdrant піднімається всередині
процесу. Це режим за замовчуванням, саме він і потрібен для заняття.

Якщо хочете справжній сервер із дашбордом — є ще два режими:

```bash
# 1. свій Qdrant у docker — БЕЗ ключа (образ за замовчуванням його не вимагає)
docker run -p 6333:6333 qdrant/qdrant
QDRANT_URL=http://localhost:6333 python knowledge_qdrant.py
# дашборд: http://localhost:6333/dashboard

# 2. сервер, який ЗАХИЩЕНИЙ ключем (або хмара Qdrant Cloud)
QDRANT_URL=http://localhost:6333 QDRANT_API_KEY=<ваш-ключ> python knowledge_qdrant.py
```

> **Якщо бачите `401 Unauthorized: Must provide an API key`** — ваш сервер
> піднято зі змінною `QDRANT__SERVICE__API_KEY`, тобто вимагає ключ.
> Подивитись його для локального контейнера:
>
> ```bash
> docker inspect <імʼя-контейнера> --format '{{range .Config.Env}}{{println .}}{{end}}' | grep API_KEY
> ```
>
> Для Qdrant Cloud ключ береться в консолі кластера. У вбудованому режимі
> (без `QDRANT_URL`) ключі не потрібні взагалі.

Порівняно зі списком у пам'яті додається: індекс переживає рестарт,
payload з метаданими поруч із вектором, фільтри та ANN-пошук замість
повного перебору, `score_threshold` як fail-closed на рівні БД.

### 4. До і після бази знань

```bash
python run.py 1 2
```

Дві відповіді поспіль. У першій агент говорить загальними словами, у
другій — називає «Правило 4.2» і суму 120 грн. Різниця в одному рядку:
`BASE_PROMPT + as_context(query)` у `modules/m02_rag.py`.

### 5. Ворота перед відповіддю (Self-RAG / CRAG)

```bash
python self_rag.py
```

```
«не прийшла, поверніть гроші»   → grade → RELEVANT → відповідь
«кур'єр десь подів бандероль»   → grade → WEAK
     rewrite → «Розшук бандеролі, компенсація за вкладення» → знайшов 7.3
«яка погода у Львові?»          → 0 правил → rewrite не поміг → ESC-…
```

Три запити — три різні шляхи. Між retrieval і генерацією стоять ворота:
спершу поріг (детермінований, безкоштовний), потім LLM-grade
(RELEVANT / WEAK). На WEAK агент переформульовує запит мовою правил і
шукає ще раз — це CRAG. Якщо й тоді порожньо, звернення йде оператору.
Жодного разу агент не вигадує правило.

### 6. Agentic: агент шукає сам

```bash
python rag_agentic.py
```

```
пошуки агента: ['повернення коштів за доставку затримка посилки']
```

На складеному запиті різниця стає очевидною:

```bash
python -c "
from rag_agentic import run_agentic
r = run_agentic('Посилка EE222333444UA у розшуку два місяці. '
                'Що належить за вміст і скільки чекати виплату?')
print(r['kb_searches'])"
```

```
['компенсація за втрачене відправлення розшук',
 'строк виплати компенсації після завершення розшуку']
```

Кілька аспектів — **кілька різних пошуків**. Static RAG зробив би один
top-K на весь запит і половину відповіді довелося б вигадувати. Ціна —
зайві виклики і затримка, тому на простих запитах agentic не потрібен.

> Формулювання пошуків щоразу інші, а кількість плаває між 2 і 3 — модель
> недетермінована. Важлива не конкретна фраза, а те, що запит **розбито
> на частини**, чого static RAG не робить у принципі.

### 7. RAGAS: три конфігурації на одному датасеті

```bash
pip install -r requirements-eval.txt
python ragas_compare.py
```

```
конфігурація      faithful.  relevancy  ctx_recall
lexical                0.65       0.71        0.67
vector                 0.61       0.86        0.64
agentic-vector         0.78       0.84        0.50
```

Читати цю таблицю треба обережно: **6 питань — не вибірка**. Одне питання
важить 17%, тож різниця 0.03 між lexical і vector — шум. Нижчий recall в
agentic не означає гіршої якості: він шукає вужче, у контексті менше
зайвого, і саме тому в нього найвищий faithfulness. Єдина різниця, більша
за шум — faithfulness 0.78 проти 0.61.

Цінність не в цифрах, а в тому, що ви їх тепер міряєте. Для рішень
потрібні 20–50 питань.

> **Пастка, на яку ми наступили:** якщо класти в `contexts` лише правила
> з бази знань, faithfulness падає до ~0.2 у всіх конфігурацій. Агент
> відповідає ще й фактами з бекенду (статус, дні, суми) — для RAGAS вони
> «не підтверджені контекстом», хоча агент їх не вигадав. Кладіть у
> `contexts` усе, що агент бачив, включно з tool-виводами.

> **Якщо замість оцінок приходять `nan`** — подивіться на версію Python.
> На 3.14 у парі з `nest_asyncio` ламається `asyncio.current_task()`:
> бібліотека підміняє клас задачі й пише поточну в свій реєстр, а
> вбудований `current_task()` дивиться в інший і повертає `None`. Далі
> `asyncio.timeout` мовчки обриває кожне завдання — звідси `nan` у всіх
> клітинках. Наш код `nest_asyncio` не імпортує, і на 3.12 усе рахується;
> баг знайшов Олександр Гочу на власному стеку. Лікується або поверненням
> на 3.12, або відмовою від `nest_asyncio`.

## Нюанси для обговорення

- **fail-open проти fail-closed.** У `domain/knowledge.py` порожній
  результат повертає найменш нерелевантне правило, у `knowledge_vec.py` —
  нічого. Що гірше: порожній контекст чи хибне правило?
- **RAG ≠ пам'ять.** Правила — «як у нас заведено», пам'ять — «що ми вже
  з'ясували з цим клієнтом». Пам'ять з'явиться на модулі 4.
- **Чанкінгу в нашій KB немає** навмисно: одне правило вже атомарне
  (~40 токенів). `chunking.py` показує, що буває, коли джерело суцільне.
